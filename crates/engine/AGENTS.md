# zeron-engine — o backend

Pai: [`../AGENTS.md`](../AGENTS.md)

## Purpose

Tudo que roda mesmo com a janela fechada: engine de sessões (pub/sub, run journal, recovery, watchdog de stall), doc host + executor de comandos, repos/worktrees, sync de checkout-diff, terminais (`portable-pty`), uploads, contas de agente (troca de credencial), auth (WorkOS via edge), host/peers do device room e identidade.

## Ownership

É o backend inteiro. `zeron headless` é esta crate e mais nada. Se um comportamento precisa sobreviver ao fechamento da UI, ele mora aqui — não em `zeron-ui`.

## Local Contracts

- `RunRequest.mcp` (Zeron MCP sempre ligado do upstream) é zerado em `drive_run`: grants MCP só pelo caminho `harness::workers_mcp` (sync v0.2.94 D3). O orquestrador raiz com grant `sessions` recebe ali também o `zeron mcp` (tools de chat, `ZERON_CHAT_ID` = o próprio chat); filhos, subagentes e Workers não. `ForkSideChat` corta o chat na última resposta completa e grava o divisor `MessagePart::Fork`; o primeiro run leva o histórico copiado como bootstrap. `DiscardWorkingTree` (upstream #81) está registrado mas sem UI do fork; o descarte vivo é `DiscardFiles`. `DiscardFiles` recusa com agente Working/AwaitingInput no mesmo checkout e em path versionado que é diretório (submódulo); untracked sai por `git clean -f -d` (sem `-x`), preservando ignorados dentro de pasta untracked.
- `SpawnChat` (IPC local) abre um Chat filho com a config da row do pai, `origin_chat_id` no mesmo upsert e o primeiro `Run`. `RunRequest.sessions` só é concedido a um Chat raiz elegível, com IPC realmente bound (`note_local_ipc` depois de `serve_ipc`); filhos, subagentes e Workers não o recebem. O lifecycle de Codex Voice usa esse grant apenas no orquestrador engine-owned, sem `turn/start`, user entry ou MCP de Workers. Dispatch, revive e `request_from_chat_row` sobrescrevem valor de cliente; runs de título, commit e recap permanecem sem grant. Cobertura: `tests/spawn_chat.rs`, `tests/e2e.rs::spawn_chat_watch_emits_the_child_and_the_first_run_uses_the_prompt`.

- Atualizações de contexto mesclam campos reportados individualmente (`ContextUsage::merge`) antes de publicar WatchSessions e persistir. Tokens zero substituem a medição anterior; limite isolado não apaga tokens. Usage intermediário de contexto não muda status nem exige outro turno.

- Login Codex reutiliza o resolvedor de executável do harness (`CODEX_EXECUTABLE` e PATH) e compõe o PATH do filho com o diretório resolvido; não assume que o daemon herdou o PATH do shell interativo. Cobertura: `tests/codex_login_resolver.rs`.

- Imagens geradas são importadas antes de qualquer journal/broadcast/fold, inclusive eventos de subagente. Intake limita a 24 MiB, identifica raster pelo header, prende a abertura ao diretório permitido do Codex e publica somente o path em uploads do perfil. Replay de imagem já persistida não exige que a fonte ainda exista; erro vira resultado de tool falho e aviso visível. Cobertura: `uploads::generated_image_tests`, `tests/e2e.rs::generated_image_is_materialized_before_publication_and_survives_reopen` e relay em `tests/device_routing.rs::target_device_id_routes_over_the_relay`.
- Replay de imagens de subagentes semeia somente referências determinísticas persistidas, com proteção contra ciclos e limites de 256 docs e 32 níveis. `DocHost::read_local_doc` lê snapshot/outbox locais sem abrir handles nem entrar em rooms históricas; a admissão respeita o limite antes da leitura.
- Materialização de anexos resolve a referência `pending://` tanto no trailer comum quanto no atributo XML `image` de Appshots, preservando o escape XML do path de destino. O mesmo contrato vale para Run e Steer.

- `GenerateCommitMessage` autoriza o checkout pelo mesmo gate de Changes, captura só `git diff --cached` via `ProcessRunner` (sem ext-diff/textconv, teto 46.000 bytes com truncagem declarada) e executa geração isolada em diretório temporário, read-only, sem Workers MCP ou resume. Usa o harness de títulos se habilitado/suportado, senão Claude Code/Codex habilitado, com o modelo econômico existente. Budget total de 90s inclui captura/catalog/model; resposta JSON subject/body validada, teto de saída 16 KiB no coletor compartilhado com recap. Não escreve em Git, Chat Transcript ou Run Journal.

- **Update de CLI de agente (upstream #389/#596) mora em `harness_updates.rs`.** `HarnessUpdateCoordinator` checa/aplica updates por harness sob o gate do registry: todo subprocesso de harness segura `registry.execution_lease(id)` (runs em `drive_run`, discovery de models/commands/skills, título, recap e commit message — os três últimos adquirem a lease uma vez e a passam para `discover_models_with_lease` e para o run), e o update pega `update_lease` exclusiva. Steer comum só entra no mailbox via `while_update_clear`; com update pendente o prompt cai no run novo atrás dele. Notificação genuína de Worker (id `worker-notify-message:*` e prompt `[worker-task-notification]`) entra diretamente no mailbox steerable existente, mesmo com update pendente: o run mantém a execution lease, e o instalador continua esperando a lease exclusiva. É o **único** updater de CLI de agente (a manutenção de Workers foi fundida nele — change `unify-agent-cli-updates`): OMP é monitorado (npm `@oh-my-pi/pi-coding-agent`, `omp update`), só Kimi fica fora (`monitored`). Codex sem install standalone atualiza pelo gerenciador que é dono do binário (`codex_package_manager_update`: `bin/npm` do prefixo npm ou `brew` ao lado do Caskroom, nunca via PATH). Os 6 RPCs estão no `method.rs` (forwardable; `CheckHarnessUpdates` 4 min, `ApplyHarnessUpdate` 20 min).

- O catálogo `Repos::refs` exclui `HEAD` remoto, preservando branches locais/remotas normais e a marcação da branch padrão pelo destino de `origin/HEAD`.
- `Repos::repository_identity` agrupa clones/worktrees pelo commit raiz (`commit:<sha>`), usa remoto normalizado e depois hash device-local do common git dir quando a história não identifica a raiz, e acrescenta o prefixo para separar subpastas de um monorepo. Falha de Git não troca silenciosamente o identificador: o Space conserva o último valor.

- Git History pesquisa apenas refs públicas em ordem topológica, com paginação e pontas de branches independentes da página. Comparação ahead/behind consulta refs locais e nunca faz fetch implícito. Toda chamada Git continua no ProcessRunner. Metadados/avatar GitHub são best-effort, com timeout e limites durante a leitura; RPC de imagens limita o total bruto a 512 KiB.

- Git deixou de ser só leitura/topologia. `Repos` também stage/unstage/discard/commit/push/pull/sync (publish com `--set-upstream` quando não há upstream), sempre por `ProcessRunner`, com `GIT_TERMINAL_PROMPT=0` em rede. Ahead/behind de Source Control lê `@{upstream}` local e nunca faz fetch. `CheckoutDiffSync` publica `CheckoutStatus` no mesmo evento de fs que recaptura o diff. Os RPCs de Source Control resolvem o cwd por `authorized_checkout` (Chat/Space deste device, ou checkout Worker cujo link `space_id` aponta para um Space deste device — `zeron_workers_unpeel::space_links::linked_checkouts_at`; estar no working set de Workers não autoriza) antes de `checkout_identity` — pathspec vai como `:(literal)`, o porcelain v1 `-z` consome exatamente um espaço após XY, e rename `-z` é dest\0source. Argv literal: FakeGit em `repos.rs` (`source_control_argv_uses_literal_pathspecs`); ahead/behind real: `upstream_divergence_reads_local_ahead_and_behind_without_fetch`; efeito RPC: `tests/source_control_ops.rs`; autorização/path: `tests/source_control_hardening.rs` (inclusive `source_control_authorizes_a_worker_worktree_of_a_local_project` e `source_control_rejects_a_folder_with_no_project`).

- `EngineCore.previews` é device-local: boot observa cwds dos Chats locais, disconnect cancela sinalização/proxy e shutdown aguarda. `WatchPreviews` consulta o catálogo do viewer e filtra pelo Chat/device dono; `targetDeviceId` aqui seleciona dados e não provoca relay RPC. Auth fornece token fresco na conexão, sem copiá-lo para o catálogo.

- `workspace_files.rs` é o acesso da árvore Files por checkout autorizado: listagem paginada (500 entradas/página), busca limitada, leitura de texto limitada a 8 MiB (inclusive após crescimento concorrente, com `TooLarge`), watcher compartilhado/cancelável, e mutações jauladas (`create_entry`/`delete_entry`/`move_entry`) em `spawn_blocking`. Path ainda inexistente passa por `WorkspaceRelativePath::planned`: cada componente é validado e o resolve recusa absoluto/`..`/`.git`/symlink (folha e meio; o backend local da UI faz a mesma caminhada com `symlink_metadata`, sem `canonicalize` do relativo). Colisão usa dobra Unicode (`to_lowercase`), não ASCII. Desde o sync v0.2.102, move e delete são os do upstream #514: validam checkout, revisão e tipo esperados, e passam pelo mesmo gate de escrita por checkout que os saves. Delete é permanente, sem Trash. A leitura Unix abre cada componente por `openat` com `O_NOFOLLOW`, diretórios por descritor e folha com `O_NONBLOCK`; valida arquivo regular e revisão pelo descritor antes de ler, recusando substituição por symlink/FIFO ou outra identidade. Plataformas sem abertura segura recusam a leitura. Toda operação valida ownership do Chat/Space e path relativo; nunca usa esse contrato para restringir links locais absolutos do Chat. A baseline do watcher e publicação usam o mesmo lock de sequência, inclusive no recovery por lag. Desde o sync v0.2.83 o upstream `ReadWorkspaceImage` e `WriteWorkspaceFile` (editor de Files) também passam por aqui, com a mesma validação de ownership e path relativo.

- **Boot recovery não liga a room de todo Chat journalado.** `sweep_abandoned_streams` lê o snapshot local (`peek_needs_abandoned_recovery`) e só chama `open()` — que faz join WS/HTTP — quando este device deixou uma entry assistant `streaming`. O peek não deve abrir handles nem iniciar rede; regressão em `doc_host::tests::peek_does_not_open_a_handle_and_skips_settled_snapshots`. `recover_stale` continua abrindo só os journals sem `Done`.
- **`raise_nofile_limit`** sobe o soft `RLIMIT_NOFILE` até o hard max no start do binário, antes do gpui. O teto de dials concorrentes mora em `zeron-sync`.
- `EngineChatSink` só persiste cursor de row cuja história causal foi aplicada. Import com dependências pendentes pede checkpoint ao cliente; checkpoint incompleto falha sem gravar cursor. Operações estacionadas pelo Loro não entram no snapshot, então cursor contíguo da room sozinho não prova durabilidade. A certificação do cursor (`ChatPersistence::cursor_verified`) é **viva**: nasce do marcador do store e vira verdadeira na primeira gravação verificada. O handle quente sobrevive às rotações do scheduler, e um booleano capturado na abertura fazia cada re-admissão repetir o "one-time legacy cursor repair" e rebaixar o cursor ao checkpoint. Regressão: `chat_persistence::tests::first_verified_write_certifies_the_warm_handle`.
- Publicação chat2 tem outbox durável por Chat: o `EngineChatSink` recarrega batches estáveis após eviction/restart, ACK só aposenta o batch depois de apagar o registro SQLite e rejeições permanentes sobrevivem até um checkpoint que cubra sua frontier. A subscription local é instalada antes do join e mantém o journal durante `disconnect_edge`; updates legacy são quebrados em rows limitadas no primeiro bootstrap.

- `respond_input` enfileira `InputResolved` com as respostas antes de liberar o runtime; a resolução órfã grava as mesmas respostas no documento antes de retomar o Chat.

- **Executor é gated por ownership do chat**: só o device host de um chat executa comandos dele. Marcar como processado vem **antes** de executar, nunca depois.
- **`Mutate retireDevice` aposenta um device duplicado.** `WorkspaceHost::retire_device` valida tudo antes de escrever: não é o device local; não está online (row com `lastSeenAt` nos últimos 70 s — a janela de Settings → Devices — ou presença fresca); toda pasta de Space dele existe aqui; nenhum Space local já cobre a mesma pasta canônica. Recusa nomeia pastas/projetos e não muda nada. Aceito, `RegistryDoc::retire_device` grava num batch só: cada Space move para o device local (mesmo id/nome/path/`createdAt`, Git limpo para o `SpacesSync` re-carimbar), cada chat e row de sessão desses Spaces segue, e o tombstone `retiredDevices/{id}` some o device de toda listagem (UI, `WatchDevices`, chat MCP `list_devices`). Cobertura: `tests/device_retirement.rs`.
- **O endpoint IPC que a engine abre vai para o controller de Workers.** `SessionsEngine::note_local_ipc` registra também `zeron_harness::note_workers_engine_endpoint`, que o harness passa como `COMET_WORKERS_ENGINE_ENDPOINT` ao `__workers_mcp__` — é por ele que o controller lista e cria projetos (Spaces). Cobertura cross-surface: `tests/project_registry.rs` (chat MCP × controller sobre a mesma engine).
- Comando é entrada durável no session doc, não chamada direta — send/steer/interrupt/respondInput passam pelo ledger. Envio offline enfileira no doc.
- **Fila pausada (Cancel/recuperação) só congela o que o usuário digitou.** Steer comum em harness de fim de turno vai para a fila (upstream v0.2.83); notificação genuína de Worker usa diretamente o mailbox steerable vivo, inclusive nesse modo. Com run ativo sem mailbox steerable, inclusive na promoção explícita de aviso genuíno já retido, o aviso aguarda o fim sem interromper o run. Sem run vivo, notificação de Worker (`worker-notify-message:*`) sai como próximo turno mesmo com a fila pausada (`drain_paused_worker_notifications`). Teste: `message_queue::a_frozen_queue_still_delivers_worker_notifications`.
- Fila com id determinístico (`queue_command_with_id`, `QueueWorkerNotification`) é **idempotente no doc**: existindo entrada com aquele id, o retry reusa a entrada e só re-dirige a entrega. O ledger de processados barra apenas a re-execução — um gêmeo `pending` fica inalcançável no doc para sempre e o dead-command sweep o reporta em todo drain (2026-08-25: ~2 800 gêmeos de um `worker-notify`, doc de 13 MB, warning `command consumed but never resolved` em loop).
- Só `AgentEvent` durável entra no run journal; `ToolCallPreview` limitado é broadcast/fold sem journal, e o `ToolCall` autoritativo é a única cópia completa do input de arquivo.
- Fechamentos confiáveis de segmentos parent/subagent persistem `duration_ms` medido pela engine; recovery não deriva duração de session rows mutáveis.
- Privacidade de input de arquivo: a projeção no session doc retém só o preview limitado de Write/Edit; o input não sanitizado permanece apenas no run journal local deste device. `FetchToolInput` limita o `ServerFrame` unary completo a 1 MiB e só lê após validar ownership local do chat.
- Lookup histórico lê JSONL do tail em chunks reversos, via `spawn_blocking`, com carry absoluto de 8 MiB + 64 KiB; tail oversized/malformado torna o input indisponível em vez de buscar corpo antigo ou alocar sem limite.
- Doc host mantém um LRU de docs; evicção faz flush do snapshot. **Falha de flush tem que ser reportada** — engolir a falha na evicção perde o snapshot da sessão com o handle já fora do mapa (`doc_host.rs`).
- Terminal: `OpenTerminal` roda o **shell de login interativo**, que volta ao prompt em vez de sair. Sem terminar o shell, `TerminalEvent::Exit` nunca é carimbado e quem espera o fim nunca completa. Payload que funciona: `exec /bin/sh -c '<script quotado>'`.
- Nada de bloqueio em contexto async (`rpc.rs`, `repos.rs` já cobraram esse preço). Trabalho síncrono vai pra `spawn_blocking` com timeout.
- **Nada de buffer graúdo vivo através de um `.await`.** Ele passa a morar *dentro* do future, e build debug reserva esse tamanho na stack de todo frame que constrói o future — inclusive o match de ~100 braços de `EngineRpc::handle`, que em `-O0` dá slot próprio a cada braço. Um chunk de leitura de 64 KiB em `diff_sync::capture_git` custava 128 KiB de frame em `capture_diff` e 832 KiB + 796 KiB nos dois frames do handler: o primeiro checkout-diff abortava o app com `tokio-rt-worker has overflowed its stack` (a worker do gpui_tokio tem os 2 MiB default). Leia direto no `Vec` de saída (`take(cap + 1)` + `read_to_end`); `diff_sync::future_size_tests` guarda o teto.
- **`process.rs` é o runner de subprocesso de source control da engine.** `Repos::git`, `diff_sync::capture_git` e o CLI de change request (`source_control.rs`) só falam com git/gh por um `ProcessRunner`; é esse trait que um teste troca por fake (`Repos::with_runner`) em vez de plantar fixture git. Toda `ProcessRequest` carrega deadline, `output_limit` e `kill_on_drop` (`false` só em `Repos::git`, porque clone/checkout/fetch precisam terminar mesmo se o handler RPC for abortado; capturas de diff e `gh` morrem com o future), e **estourar o teto mata o child** em vez de drenar o resto — sem isso um `git diff` de repo gigante fica produzindo saída que ninguém quer. Mutações de worktree passam pelo `git_command` com deadline próprio em `workers-unpeel`; os demais spawns diretos da engine são `security` (Keychain) em `agent_accounts.rs`/`antigravity_usage.rs`, `codex login`, `scutil` em `lib.rs`, e `diff_sync::snapshot_tree` (índice temporário via `GIT_INDEX_FILE`).
- **Chat e Workers compartilham o ciclo de vida de worktree em `workers-unpeel`.** `Repos::create_worktree` e `CreateWorktree` chamam o serviço por `spawn_blocking`; após 720s a engine registra aviso e espera a mutação concluir para não devolver um falso timeout enquanto ela ainda altera o disco. Cópia opt-in de `.worktreeinclude` precede setup e `pre-start` no preparo pendente; falha mantém o checkout para retry. Setup e `pre-start` têm orçamento total de 300s cada. A engine grava no mesmo journal de ownership usado por Workers, nunca num arquivo derivado do `data_dir` do perfil. Em um Run com `WorktreeSpec`, `PendingChatCheckout` mantém a reserva de preparo enquanto o host grava `cwd`/branch, antes de executar cópia/setup/hooks. Se o preparo falha, o checkout e a associação ficam; o handoff de Project Actions termina com erro, sem iniciar action terminal. Um Run comum posterior chama `prepare_checkout_for_chat` para retry idempotente no mesmo checkout. Um checkout comprovadamente fora da raiz atual e das raízes históricas do app é externo e pula o journal; dentro de qualquer raiz possível, erro de journal (caminho indisponível, ilegível ou identidade divergente) falha o Run em vez de pular cópia/setup/hooks. Terminal aberto dentro de um checkout linkado reserva o checkout só contra remoção física; `Terminals::shutdown` libera essas reservas de forma síncrona. `DeleteWorktree` resolve o path contra `git worktree list --porcelain` antes de delegar. Checkout presente exige journal Owned, nenhuma atividade local, árvore limpa e os hooks aprovados; não usa `--force` nem fallback recursivo. Depois da remoção, a branch local só sai quando comprovadamente integrada à branch padrão, desocupada e ainda no OID avaliado; caso contrário permanece. Para leaf ausente, a engine exige registro no porcelain e parent acessível antes de chamar a API compartilhada de prune; ela revalida journal e estado sob o action lock, remove apenas metadata Git stale e preserva branch. Path sem registro, parent inacessível ou probe que falhou não vira autorização para remoção. `CheckoutQuery::Workspace` continua sendo uma pergunta distinta: aceita o repo principal, mas exige checkout existente; `canonicalize_lossy` compara ancestrais existentes e reaplica a cauda em registros stale. Os cenários end-to-end vivem em `tests/{m5_repos_diffs_terminals,worktree_on_run}.rs`; os probes puros em `repos.rs`.
- **O git local de `Repos` passou a ter teto, e isso é mudança de comportamento.** Antes da fase C, `Repos::git` rodava `Command::output()` sem deadline nem limite: só o caminho de relay tinha teto. Hoje toda invocação carrega `LONG_GIT_TIMEOUT` (15 min) e `GIT_OUTPUT_LIMIT` (16 MiB), então clone de repo gigante em rede ruim passa a falhar com `git clone timed out` em vez de continuar indefinidamente — decisão consciente: um clone pendurado segura o slot de RPC e a UI fica sem resposta, enquanto o timeout é observável e retryável. Mexer nesses tetos é mudar contrato de usuário, não constante interna.
- `CheckoutDiffSync` adquire pins na mesma seção crítica de `entries` que consulta/cria a entrada. `add_entry` reutiliza entradas existentes; reconciliação não remove entradas pinadas, e o último release devolve o checkout ao grace normal.
- **Dispatch de modo de diff mora em `diff_sync`, não no match do RPC.** `DiffMode::parse` traduz o trio de fio (`mode` + `baseRef`/`commitSha`/`chatId`) com as mensagens de erro exatas que a UI já conhece, e `capture_for_mode` / `capture_with_base_for_mode` / `recapture_for_mode` são os únicos lugares que escolhem entre working tree, branch, commit e turn. Escopo novo = braço novo no enum, nunca um `if` no handler.
- Auth passa pelo edge (WorkOS): a engine não guarda segredo de OAuth próprio.
- Usage de providers combina janelas remotas com totais locais limitados de arquivos Claude/Codex. Esses snapshots são device-local e trafegam só no RPC engine→UI; nunca entram no session doc nem no sync. Probes forçados preservam as últimas janelas bem-sucedidas (*last-known-good*) em falhas transitórias para evitar que o indicador suma. O backoff de falha transitória (429, 5xx, rede) **escala** por entrada (`UsageEntry.failures`: dobra até 30 min, Retry-After maior vence, sucesso zera); falhas de credencial mantêm espera fixa. Sem isso, `429 Retry-After: 0` virava probe a cada refresh do widget (150s) por horas. O log é do fold em `refresh_usage`: `warn` na primeira falha ou troca de classe, `debug` enquanto repete, `info` na recuperação.
- **AgentAccounts:** troca de slot de credencial por harness. No macOS o Claude tem DOIS stores — o item do Keychain de login (via a máquina `security` em `agent_accounts.rs`) e `$CLAUDE_CONFIG_DIR/.credentials.json` — e qualquer um pode ser sobra velha, então **não há precedência fixa**: a leitura pega o store com o `claudeAiOauth.expiresAt` mais recente (Keychain vence empate e blob sem data), e a escrita cai em TODO store que já tem login, para que a troca não seja desfeita pela próxima virada de expiry. Fora do macOS (e sempre que a config traz paths explícitos de teste) só o arquivo é usado. Codex: `auth.json`. Grok: `$GROK_HOME/auth.json` do `grok login` (OIDC grok.com), nunca o `apiKey` de `user-settings.json`.
- **Título nativo OMP:** sem override explícito de harness para títulos, o Chat OMP usa o título emitido pela própria CLI ao finalizar o turno. `RunControls.generate_native_title` só é habilitado para Chat sem nome e sem override de harness de títulos. `NativeTitle` é consumido antes de journal/broadcast e reaproveita a proteção de rename manual e nomeação de branch. Não dispara o gerador de títulos do Comet no dispatch nem consulta outro modelo no Done; ausência do título nativo usa somente fallback textual. Claude/Codex mantêm preferências explícitas e seleção existente.
- **Título de chat fala a língua do usuário:** o prompt de titling manda escrever na MESMA língua do request e capitalizar como aquela língua capitaliza título. Pedir `Title Case` sem regra de língua, como era antes, dava título em inglês para sessão inteira em português — a instrução em inglês em volta do request vencia o idioma dele — e `Title Case` é convenção só do inglês (PT/ES/FR capitalizam primeira palavra e nomes próprios, então impô-la escreve errado um título já correto). O fallback continua sendo as primeiras palavras do próprio prompt, que já vêm na língua certa.
- **Idle Chat recap:** `recap.rs` deriva o resumo sem alterar a Session ativa. O contrato de execução isolada e seleção de harness está no [pipeline de recap](../../docs/plans/2026-09-05-idle-session-recap-design.md#22-engine-recap-pipeline-cratesenginesrcrecaprs).
- **Kimi managed Usage:** Kimi é identidade de conta/Usage ativa e não trocável, nunca um harness executável nem login próprio do app. Produção lê só `${KIMI_SHARE_DIR:-~/.kimi}/credentials/kimi-code.json`, faz refresh sob o `kimi-code.lock` irmão com seis tentativas não bloqueantes (cinco backoffs de 1.5s), re-leitura pós-lock e substituição atômica `0600`. Requests Bearer vão só para `https://api.kimi.com/coding/v1/usages`; redirects são desabilitados. Cada row de quota (`usage` e `limits[].detail`) vira janela a partir de `used` quando a chave existe e de `limit - remaining` quando não — o endpoint trocou de `used` para `remaining` e o parser que exigia `used` derrubava o payload inteiro, pintando quota cheia como "No usage yet". Janelas bem-sucedidas ficam 60s em cache, invalidado por force refresh, mudança/remoção de credencial ou TTL. Credencial e janelas ficam fora do Loro e do sync do edge; erros expõem só warnings seguros ao provider.
- **Cursor managed Usage:** Cursor é identidade de conta/Usage com janelas de quota lidas de **dois logins device-local, nessa ordem**: (1) o store do app desktop (`state.vscdb`, `cursorAuth/accessToken` e `cursorAuth/cachedEmail`); (2) o login da CLI `cursor-agent` no Keychain do macOS (serviço `cursor-access-token`, conta `cursor-user`), com o email da conta vindo de `~/.cursor/cli-config.json` (`authInfo.email`). O desktop vence quando os dois existem, porque é o app da Cursor que mantém aquele token fresco. Ler o token de conta inteira da CLI **era proibido de propósito** e passou a ser feito porque em máquina com CLI e sem app desktop — setup comum — não existe outra fonte, e a linha ficava vazia ao lado de um `cursor-agent` que mostra a quota. A API key do SDK (`crsr_…` em `~/.cursor/sdk/auth.json`) **não** é alternativa: autentica apenas o Cloud Agents API e esse endpoint responde `401 ERROR_NOT_LOGGED_IN` a ela. Requests para `POST https://api2.cursor.sh/aiserver.v1.DashboardService/GetCurrentPeriodUsage` usam bearer, `Connect-Protocol-Version: 1`, body `{}` e timeout de 8s; redirects são desabilitados. `planUsage.totalPercentUsed` (depois `autoPercentUsed`, senão `totalSpend`/`limit`) vira uma janela `Monthly` com `resets_at = billingCycleEnd` — o percentual do dashboard, não o teto em dólares do `includedSpend`. Os dois stores são estritamente read-only — o app desktop e a CLI cuidam do refresh, a engine nunca grava; o construtor de teste (`from_paths`) nunca cai no Keychain real. A quota anexa à conta do Cursor com o mesmo email da sessão desktop, caindo na conta ativa se a sessão não trouxer email.
- **Antigravity managed Usage:** Antigravity (Gemini) é identidade de conta/Usage ativa e não trocável, nunca um harness executável nem login próprio do app. Requests para `https://cloudcode-pa.googleapis.com/v1internal:retrieveUserQuotaSummary` exigem body `{}` e o User-Agent `antigravity/hub/2.9.1 darwin/arm64` — **o UA é o gate de licença**: sem o prefixo `antigravity` a Google responde `403 PERMISSION_DENIED "You do not have a valid license of this product"`, e `reqwest` manda UA próprio por default. Janelas são normalizadas na ordem `Weekly`, `5h`, `Weekly (Claude/GPT)`, `5h (Claude/GPT)`, identificando o grupo por prefixo de `bucketId` (`gemini-`/`3p-`), nunca por `displayName`. Refresh via `POST https://oauth2.googleapis.com/token` com o client público do Antigravity fornecido em runtime pelo par completo `COMET_ANTIGRAVITY_CLIENT_ID`/`COMET_ANTIGRAVITY_CLIENT_SECRET`; material OAuth nunca entra no source nem no artefato. Sem o par, access token ainda válido segue usável e somente a tentativa de refresh degrada para warning redigido. A Google **não rotaciona** o refresh token nesse fluxo, então o access token vive só em memória e nada é gravado em credencial de terceiro. Um `401`/`403` de quota renova o access token e refaz o fetch **no mesmo snapshot** (uma única vez), preservando o refresh token e as demais credenciais do pool.
- **Precedência de credencial do Antigravity no widget de Usage de uma linha antiga era por STORE.** Settings → Accounts lista o **pool inteiro**: cada `~/.cli-proxy-api/antigravity-*.json` usável e o login do Keychain quando o email é outro. CLIProxyAPI roteia; nenhuma row é a conta ativa singular. Não existe mais caminho de credencial única nem precedência entre stores. Keychain duplicado pelo mesmo email não vira segunda row. Cada login tem cache próprio de Usage (TTL 60s, chaveado por refresh token + email para sobreviver ao refresh do access token); `forceUsage` ignora o cache.
- **Grok managed Usage:** Grok é identidade de conta/Usage ativa lida do `$GROK_HOME/auth.json` (padrão `~/.grok/auth.json`, gravado por `grok login`), nunca o `apiKey` de `user-settings.json`. OIDC refresh bate em `POST https://auth.x.ai/oauth2/token` sob o lock irmão `auth.json.lock` com re-leitura pós-lock e substituição atômica `0600` preservando todas as entradas e campos irmãos. Quota consulta `GET https://cli-chat-proxy.grok.com/v1/billing?format=credits` (timeout de 8s, redirects desabilitados); mapeia `USAGE_PERIOD_TYPE_WEEKLY` / `USAGE_PERIOD_TYPE_MONTHLY` para janelas `Weekly` / `Monthly`. **Conta sem quota própria não é payload inválido**: a x.ai responde 200 com `config` bem formado e sem `creditUsagePercent` para planos sem teto próprio (unified team billing — `monthlyLimit`, `onDemandCap` e `prepaidBalance` zerados), e as demais `format=` respondem contadores + `billingPeriodStart` sem `currentPeriod` nenhum. Esses casos viram zero janelas **sem warning**; só resposta fora do shape do endpoint (sem `config`, tipo de período desconhecido, percentual negativo/não-finito) levanta `UsagePayload`. Tratar os dois como erro punha aviso vermelho redigido numa linha saudável. Janelas válidas ficam 60s em cache; falha transitória de probe forçado após sucesso serve a última medição conhecida (*last-known-good*) com warning seguro; rotação ou remoção de credencial invalida o cache. Credenciais e tokens nunca saem do módulo, nunca entram no Loro nem sincronizam com o edge.
- **Marcador de troca de modelo é entry `system` no session doc**, escrito por `ChatDocHandle::write_model_switch` a partir de `Mutate noteModelSwitch`: part de texto (cliente antigo lê como linha comum, não descarta a entry), no-op com transcript vazio, e sem `note_message` — o marcador não move a freshness do row na sidebar. Os labels vêm da UI porque o catálogo de modelos não existe aqui. `Mutate noteMarker` é a mesma escrita com texto livre do chamador (`write_marker`) — é por ela que a UI grava o marcador de compactação, cujos números de token só ela conhece.
- Context usage é last-known por chat: iniciar um novo processo preserva a última
  medição até o runtime emitir outra; update ausente nunca apaga o indicador.
- Checkout local ou sem identidade GitHub é estado suportado: `UnsupportedRepository` no refresh de change request fica em debug; falhas operacionais de CLI, autenticação, quota, timeout, decode e comando continuam em warning e preservam o último sucesso.
- **`SearchFiles` é indexação bounded por checkout**, não caminhada por tecla: resolve exatamente um `chatId` ou `spaceId`, valida a raiz/target device, serializa builds concorrentes por raiz e reaproveita o índice enquanto a assinatura do checkout não muda. Query é limitada a 256 caracteres; resultados são relativos, fuzzy-ranked e respeitam os ignores do repositório. A UI trata RPC ausente em daemon antigo como estado compatível, não como lista vazia autoritativa.
- Motivo de falha é espelhado na session row (`Session.error`) na **mesma transição** que carimba `Errored`, e qualquer transição não-erro o limpa — reason velho não sobrevive ao turno seguinte. O campo é live-only: trafega no `WatchSessions` do device que rodou, nunca no session doc.
- **Journal fechado com `Done` não prova que o doc assentou**: `publish` grava no journal de forma síncrona enquanto o fold no doc (e o snapshot debounced) chegam depois. Boot recovery varre os dois conjuntos — os journals stale (`stale_sessions`) e **todo** chat journalado (`journaled_chats` → `sweep_abandoned_streams`). Sem o segundo passe, um crash nessa janela deixava a entry `streaming` para sempre: spinner de "Thinking" eterno e pergunta que o fallback de `RespondInput` recusava. Doc ilegível pula o chat, nunca aborta a varredura dos outros.
- **Carimbar a entry `aborted` não assenta as parts dela.** As duas varreduras passam por `mark_abandoned_streams`, que chama `settle_pending_parts`: tool sem resultado resolve como erro, subagente `running` vira `failed`, reasoning completa, input pendente resolve. Sem isso o card ficava girando embaixo do próprio aviso de interrupção. A decisão vem da entry LIDA, nunca do mapa Loro cru — `resolved` é derivado na leitura, e julgar por presença de chave marcava como erro tool que terminou bem.
- **O doc do subagente assenta junto com o chip dele.** O run morto nunca fecha os sinks, então o doc `chat--sub--*` ficava com a última entry `streaming`. Com isso a aba do subagente girava para sempre, enquanto o chip no pai já tinha virado `failed`, e o widget Details e a aba discordavam (user report). As duas varreduras chamam `settle_orphaned_subagents`: chip ainda `running` (subagente de fundo cuja entry já tinha fechado) vira `failed` com `subagentEnd` na última entry gravada, e todo chip assentado nesta recuperação tem as streams abandonadas do doc dele carimbadas `aborted`. Só abre os docs desses chips, nunca de todos os subagentes do chat. Se o subagente voltar de verdade no run retomado, a abertura do sink reabre chip e doc como `running`. Regressão em `restart_resume::recovery_settles_subagent_docs_in_step_with_their_chips`. Desde o sync v0.2.102 as duas varreduras chamam `ChatDocHandle::recover_abandoned`, que junta o sweep do upstream (#676) com o do fork e devolve `AbandonedRecovery { stamped, failed_chips }`: só chips **deste device** são assentados (chip de run de outro device continua `running`, `e2e::recover_stale_journal_settles_chips_in_completed_local_entries`), e o `settle_orphaned_subagents` só aborta os docs a partir desse retorno, sem virar chip por conta própria.
- Fallback órfão de `RespondInput` é gated por `has_live_run`, não pelo status da entry: com run vivo o guard de entry `streaming` continua (resolver recém-consumido não pode virar turno duplicado); sem run vivo não há nada pra correr, então pergunta aberta em entry `streaming` é respondível e entra como turno novo.
- O rail de anexos queued é content-agnostic: bytes de imagem ou texto chegam pelo mesmo `pending://`, são materializados no device do run e têm o path absoluto reescrito tanto em `RunRequest.attachments` quanto no trailer do prompt.
- Codex realtime voice usa um bridge host-local por runtime. `SessionsEngine::start_voice_idle` cria/retoma o app-server sem `turn/start`, user entry ou pedido de título; somente o Chat de orquestrador engine-owned recebe o `SessionsGrant` raiz já existente, depois do bind IPC local, com Workers MCP desligado e `RunRequest.mcp` vazio. Runs comuns e Workers children não recebem essa autorização por prompt. Uma sessão Codex compatível já viva é reutilizada. A atividade de call segura o reaper e impede que atualização aposente o runtime em uso.
- **Shutdown de sessões interrompe Chats independentes em paralelo.** Cada `interrupt` continua com seu próprio limite de assentamento de 5s; `SessionsEngine::shutdown` espera todos concorrentemente para que o tempo total não some esse limite por Chat.
- **Admissão de runs e terminais é coordenada atomicamente com o RestartGate**: `dispatch` e `open_with_shell` adquirem um guard RAII de admissão contada (`reserve_admission`) antes de iniciar setup assíncrono através de awaits, transferindo a proteção para o registro ativo em `runs` ou `sessions`. Durante o setup em voo ou com trabalho ativo, o `RestartGate` rejeita autorização de restart com `WorkActive`; com restart autorizado pelo updater (inclusive durante a janela de 800ms antes da terminação do serviço), qualquer nova admissão é rejeitada com erro; falha ou cancelamento no apply/restart libera o gate.
- **`WatchSessions` merge deixa o live local ganhar do próprio row persistido, e o mapa de statuses nasce vazio no boot.** Por isso `EngineCore::assemble` chama `sessions.hydrate_persisted_statuses(workspace.read_sessions())` **antes** de `recover_stale`: sem esse seed a janela de contexto de uma sessão assentada zerava até o próximo turno medir de novo (user report). O seed só entra rows deste device, pula chat que um run vivo já reivindicou, e normaliza `Working`/`AwaitingInput` persistido para `Idle` (nenhum run está vivo no boot; `recover_stale` reativa/resume os genuinamente em voo logo depois). `set_status` preserva `context_usage` do entry, então a ordem seed→recover mantém a medição.
- **A Trajectory foi removida (2026-10-05, `openspec/changes/remove-chat-trajectory/`).** `EngineCore::assemble` só apaga, best-effort, os restos `trajectory.sqlite3`/`-wal`/`-shm` do store do perfil (`cleanup_removed_trajectory_store`); falha vira `warn` e nunca derruba o boot. Não reintroduzir captura em `publish`.

- Claude/Codex automatic Chat titles use an isolated temporary directory and `Harness::run_title`, with tools disabled, explicit device-local harness/model preferences, shared retry deadline, language preservation and prompt fallback. Concurrent requests for one Chat are deduplicated; user renames win.

- Completion markers publish atomically with status/error and survive hydration. Pending accepted steers suppress internal-handoff completion; mailbox acceptance and ledger insertion are serialized. Quiescence publishes completion only for nonempty output without pending steers.
- Model discovery com catálogo em disco espera a lista viva só 100ms e serve o disco; esse caso é `debug` ("Model discovery deferred"), não falha — o refresh continua e loga "Model discovery failed" se de fato falhar. O warning restante carrega `reason` legível, nunca `Option` em debug.
